============================================================
LOGFORGE AI — COMPLETE PHASE 1–9 PROJECT CONTEXT
============================================================

PROJECT:
LogForge AI — Universal Adaptive Log Pre-processing Framework (ULPF)

CORE IDEA:

Any Log
   ↓
Detect
   ↓
Parse
   ↓
Normalize
   ↓
Preserve
   ↓
Verify
   ↓
Learn
   ↓

LogForge is designed to solve the problem of different vendors and systems producing different log formats, fields, structures and behaviors.

The system converts heterogeneous logs into a common, traceable and lossless representation while allowing unknown vendors and changing log structures to be safely learned over time.

IMPORTANT PRINCIPLE:

"Never silently lose evidence."

The original/raw event must remain recoverable even when parsing or normalization is incomplete.

STEP 10B — HORIZONTAL SCALING + LOAD BALANCING
============================================================

PURPOSE:

Add horizontal application scaling behind a load balancer while
preserving the complete LogForge evidence and processing guarantees.

The load-balancing layer must not change the meaning or integrity of
any event. Every request must continue through the same LogForge
pipeline and shared persistence path.

IMPORTANT DESIGN RULES:

- Do not redesign the core ingestion pipeline.
- Do not introduce Kafka, Redis, Kubernetes, Celery, RabbitMQ,
  OpenSearch, MinIO, a new production database, or a new production
  queue only to implement load balancing.
- Preserve raw-event bytes.
- Preserve SHA-256 integrity.
- Preserve vault storage.
- Preserve Merkle integrity.
- Preserve normalization and field accounting.
- Preserve lineage and traceability.
- Preserve drift detection and Phase 7 governance hooks.
- Preserve idempotency and duplicate-event protection.

============================================================
LOAD BALANCING ARCHITECTURE
============================================================

                     HTTP CLIENT
                          |
                          v
                  NGINX LOAD BALANCER
                          |
             +------------+------------+
             |            |            |
             v            v            v
         Backend-1    Backend-2    Backend-3/4
             |            |            |
             +------------+------------+
                          |
                          v
                      PostgreSQL

Application replicas are stateless. PostgreSQL remains the shared
persistence layer for all replicas.

Supported deployment shapes:

1. Single backend replica
2. Two backend replicas
3. Four backend replicas

The same application image/configuration is used for each replica.
Only the replica count changes.

============================================================
LOAD BALANCER RESPONSIBILITIES
============================================================

NGINX acts as the application entry point and distributes incoming
HTTP requests across healthy backend replicas.

The load balancer must:

1. Route requests only to healthy replicas.
2. Detect failed/unavailable upstreams.
3. Remove unhealthy replicas from normal routing.
4. Reintroduce replicas after successful health recovery.
5. Preserve request payloads without modification.
6. Expose upstream/request metrics for observability.
7. Support graceful worker draining during shutdown.

Initial deterministic routing can use round-robin with health checks.
The routing layer must remain independent of event-processing logic.

For future optimization, routing may use an adaptive load score based
on queue depth, active requests, latency, CPU pressure, error rate and
event complexity, but this must only replace round-robin after being
implemented and validated.

============================================================
BACKEND WORKER FLOW
============================================================

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓
Response

Every replica executes the same processing flow.

============================================================
STATELESSNESS REQUIREMENTS
============================================================

Backend replicas must not depend on replica-local state for correctness.

Do not keep correctness-critical information only in:

- process memory
- local temporary state
- local in-memory queues
- local-only databases
- replica-specific files

Shared or deterministic sources must be used for information required
across requests or replicas.

Any temporary local state must be non-authoritative and disposable.

============================================================
FAILURE HANDLING
============================================================

If a backend replica fails:

1. NGINX stops routing new requests to the failed replica.
2. Other healthy replicas continue accepting traffic.
3. In-flight work follows the existing application error/retry rules.
4. Retries must remain idempotent.
5. Duplicate delivery must not create duplicate authoritative events.
6. The failed replica can be restarted and returned to service after
   health validation.

No failure path may bypass raw preservation or integrity verification.

============================================================
BACKPRESSURE AND QUEUE PROTECTION
============================================================

Each backend must use bounded request/worker capacity.

When capacity is exhausted:

- apply controlled backpressure
- reject or defer excess work using explicit error behavior
- avoid unbounded memory growth
- preserve retry/idempotency semantics
- expose saturation metrics

Load balancing must distribute work; it must not hide application
saturation.

============================================================
GRACEFUL DRAINING
============================================================

Before stopping a backend replica:

1. Mark the replica as DRAINING.
2. Stop accepting new work.
3. Allow safe in-flight requests to finish.
4. Flush required persistence/integrity operations.
5. Remove the replica from normal load-balancer routing.
6. Shut down the process.

Startup must perform the existing health and database readiness checks
before the replica becomes routable.

============================================================
ADAPTIVE LOAD DISTRIBUTION
============================================================

The production-oriented load score may combine:

Load Score =
  Queue Pressure
  + Active Request Pressure
  + CPU Pressure
  + Latency Pressure
  + Error Pressure
  + Event Complexity Pressure

The router should prefer a healthy replica with lower effective load.

Weights must be configurable and observable. A replica with repeated
errors or severe saturation must be penalized or temporarily removed.

This adaptive policy must never alter event-processing semantics.

============================================================
DATABASE BOTTLENECK HANDLING
============================================================

Horizontal application scaling must not be treated as database scaling.

If PostgreSQL becomes the limiting layer:

- identify database CPU/connection/WAL/fsync/persistence pressure
- avoid blindly adding application replicas
- preserve the single shared database semantics
- document the database as the capacity boundary
- optimize only where the measured bottleneck justifies it

Do not introduce a second production database merely to make scaling
figures appear larger.
